# Привязка сайтов

Привязка сайтов закрепляет выбранные сайты за выбранными выходными серверами: их трафик уходит только через один из этих серверов или не уходит вовсе, какими бы ни были режим, правила и выбранный прокси. Остальной трафик идёт как обычно.

## Как работает привязка

Ядро сверяет каждое новое соединение с включёнными привязками раньше режима и правил. Соединение, попавшее под привязку, уходит через первый из её серверов, прошедший последнюю проверку задержки, а если не прошёл ни один — через первый. Если в запущенном профиле нет ни одного сервера привязки, соединение отклоняется. Привязанный сайт никогда не идёт напрямую, даже в режиме «Напрямую».

Выходной сервер запоминается по всему его определению, кроме имени, поэтому переименование сервера привязку не ломает, а серверы с одним адресом, но разными учётными данными не смешиваются. Если обновление подписки поменяло определение, привязка находит сервер по имени, но только с тем же адресом и портом: сервер, переехавший под старым именем, выходом не считается, и привязка отклоняет соединения, пока вы не выберете сервер заново. Группы прокси и встроенные DIRECT и REJECT выходами быть не могут.

## Создание привязки

Откройте **Инструменты → Расширенная конфигурация → Привязка сайтов** и нажмите **+**.

- **Имя** необязательно; без него в списке показывается первый сайт.
- **Сайты** — по одной записи на строку.
- **Исключения** — записи, которые остаются вне привязки, даже если подходят под **Сайты**.
- **Выходные серверы** — выбранные серверы; **Выбрать серверы** открывает серверы запущенного профиля с поиском по стране или названию. Одинаковые серверы под разными именами занимают одну строку. Список загружается только при работающем ядре; сохранённые серверы остаются в привязке в любом случае, а убрать сервер можно долгим нажатием или правым кликом.

| Что ввести | Как сохранится |
| --- | --- |
| `chatgpt.com`, `*.chatgpt.com` или `.chatgpt.com` | `DOMAIN-SUFFIX,chatgpt.com` |
| Вставленный адрес, например `https://chatgpt.com/c/1` | `DOMAIN-SUFFIX,chatgpt.com` |
| `geosite:openai` | `GEOSITE,openai` |
| `1.2.3.4` | `IP-CIDR,1.2.3.4/32,no-resolve` |
| `2001:db8::/32` | `IP-CIDR6,2001:db8::/32,no-resolve` |
| Правило mihomo без цели, например `DOMAIN,api.openai.com` или `DOMAIN-KEYWORD,openai` | Как введено |

Домены в национальных алфавитах, например `пример.рф`, совпадают и со своей punycode-формой. Запись `IP-CIDR`, введённая без `no-resolve`, заставляет ядро разрешать имя каждого нового соединения, чтобы сравнить его адрес, и замедляет соединения, не имеющие отношения к привязке; оставляйте `no-resolve`, если привязка не должна ловить имена, которые разрешаются в этот диапазон.

В привязке до 128 записей и до 16 выходных серверов, всего привязок — до 32. Пока ядро работает, оно проверяет весь список при сохранении привязки: если оно отклоняет запись, редактор остаётся открытым и показывает эту запись и причину, а действуют прежние привязки. Привязку, сохранённую при остановленном ядре, ядро проверяет при запуске; отклонённая тогда привязка показывается с причиной и не действует.

## Пресеты

В шапке страницы есть **Из пресета**: Claude, ChatGPT, Gemini, Grok, Perplexity, DeepSeek и Cursor. Выбор пресета заполняет **Сайты** списками geosite или доменными суффиксами сервиса и открывает редактор, где нужно выбрать выходные серверы. Эти сервисы помечают аккаунты, у которых меняется IP-адрес; привязка удерживает их на выбранном сервере.

## Статусы

| Статус | Что значит |
| --- | --- |
| Через *сервер* | Привязанные соединения уходят через этот сервер. |
| Все выходы недоступны | Все выходы провалили последнюю проверку задержки; соединения всё равно пробуют первый. |
| В профиле нет выходного сервера | В запущенном профиле нет ни одного сервера привязки, поэтому привязанные соединения отклоняются. |
| Выключено | Привязка выключена. |
| Ожидание ядра | Ядро ещё не сообщило статус этой привязки. |

## Вне туннеля на Linux

На Linux при включённом TUN и установленном Helper привязка держится ещё и в системном файрволе. Нужна команда `nft` (пакет `nftables`); без неё страница сообщает, что пакета нет. ufw, firewalld и iptables продолжают работать рядом: ReClash добавляет собственную таблицу `inet reclash_sitelock_<uid>` и не меняет их таблицы. Привязанные адреса отклоняются на всех интерфейсах, кроме TUN ReClash, в том числе на интерфейсе другого VPN. Диапазон fake-ip отклоняется только на физических интерфейсах, например Ethernet и Wi-Fi, а на других туннельных (tun, WireGuard) нет, поэтому другой VPN с тем же диапазоном fake-ip, как у других клиентов на основе mihomo с `198.18.0.0/16`, может работать параллельно. DNS-запрос привязанного имени вне TUN ReClash по-прежнему уходит в него или отбрасывается, так что параллельный VPN не откроет привязанный сайт. DNS-запрос привязанного имени он не отбрасывает, а заворачивает в туннель, и ядро отвечает адресом fake-ip: имя резолвится, а соединение уходит на выбранный выход через привязку. Остальные DNS-запросы Helper пропускает как есть, поэтому имена, известные только домашнему роутеру или другому VPN, продолжают резолвиться. Пока ядро остановлено или упало, туннеля нет, поэтому запрос привязанного имени отбрасывается и блокировка держится; при загрузке системы Helper восстанавливает её ещё до запуска ReClash. Исключения по имени действуют и здесь, а исключения по адресу — нет, поэтому такой адрес вне туннеля остаётся заблокированным. Если что-то очистит файрвол, например перезапуск службы файрвола, Helper вернёт привязку примерно за 10 секунд. Чтобы открыть привязанный сайт напрямую, выключите его привязку. Если Helper не работает, когда вы выключаете последнюю привязку, файрвол продолжает блокировать до возвращения Helper; страница об этом сообщает, а ReClash снимает блокировку, как только Helper ответит.

> [!IMPORTANT]
> Пока включена хоть одна привязка, каждый DNS-запрос вне туннеля проходит через Helper. Если Helper остановится, эти запросы тоже остановятся, а не утекут.

Чтобы посмотреть правила самостоятельно, выполните `sudo nft list table inet reclash_sitelock_<uid>`, где `<uid>` — вывод `id -u`.

В туннель уходит только запрос привязанного имени и только по IPv4 и UDP. Запрос, который Helper не может прочитать, например фрагментированный, отбрасывается без ответа, как и запрос привязанного имени по IPv6 или TCP: приложение ждёт собственного таймаута, прежде чем сдаться.

## Вне туннеля на Windows

На Windows при включённом TUN и установленном Helper привязка держится в Windows Filtering Platform и в политике разрешения имён DNS-клиента. Windows отклоняет соединения с привязанными адресами на всех интерфейсах, кроме TUN, и с DNS-адресом туннеля. Диапазон fake-ip закрыт только на интерфейсах Ethernet, Wi-Fi и PPP, поэтому параллельный VPN работает так же, как на Linux. Привязанные имена, и полные, и суффиксы, разрешает только DNS туннеля, поэтому ядро отвечает адресом fake-ip, а соединение уходит на выбранный выход через привязку; остальные имена разрешаются как раньше. Пока ядро остановлено или упало, туннеля нет, поэтому привязанное имя не разрешается и блокировка держится. Фильтры и правила переживают перезагрузку без участия Helper. Если что-то их удалит, Helper вернёт их примерно за 10 секунд, а удаление Helper их снимает. Если Helper сломан или удалён в обход деинсталляции, выполните `ReClashService.exe lift-site-lock` из папки ReClash в терминале администратора: команда остановит Helper, уберёт фильтры и правила, а также снимет [kill switch](kill-switch.md). Выключение последней привязки работает так же, как на Linux.

От Linux Windows отличается в трёх местах:

- **Ключевые слова и регулярные выражения**: политика разрешения имён знает только полные имена и суффиксы, поэтому записи `DOMAIN-KEYWORD`, `DOMAIN-REGEX` и `DOMAIN-WILDCARD`, а также ключевые слова и выражения списков geosite держатся только ядром.
- **Исключения**: вне туннеля не действуют ни исключения по имени, ни исключения по адресу, поэтому имя-исключение под привязанным суффиксом не разрешается, пока ядро остановлено.
- **Общий доступ**: трафик, который Windows пересылает для других устройств, например через мобильный хот-спот, не фильтруется.

Если политика разрешения имён на компьютере приходит из групповой политики домена, Helper добавляет свои правила в неё, и обновление политики может удалить их, пока Helper их не вернёт.

## Системный брандмауэр на странице

На Linux и Windows на странице привязок есть группа **Системный брандмауэр**: **Механизм** (nftables или Windows Filtering Platform), **Состояние** (работает или проблема), **Заблокированные адреса**, **Имена, фильтруемые по DNS** и **Fake-ip диапазоны, закрытые для физических сетей**. **Показать правила** открывает действующие правила; на Linux там же показана команда `nft` для самостоятельной проверки.

## Удаление ReClash

> [!IMPORTANT]
> На Linux и Windows привязку обеспечивает системный брандмауэр через Helper. Она продолжает работать, пока ReClash закрыт или упал, и с самой загрузки, а снимается только выключением всех привязок. Пакеты DEB и RPM и деинсталлятор Windows удаляют Helper и его правила. Для AppImage или ручной установки на Linux сначала выполните **Инструменты → Ядро → Удалить Helper** либо выключите привязки перед удалением приложения.

## На Android

На Android у привязки нет слоя в системном фаерволе, но пока привязка включена, ReClash закрывает лазейки, которые открыла бы его собственная VPN:

- **Без обхода**: приложения не могут обойти VPN, что бы ни стояло в **Инструменты → Сеть → Разрешить приложениям обходить VPN**. Настройка сохраняет значение и снова действует, когда все привязки выключены.
- **Маршруты**: привязанные адреса и диапазоны fake-ip профиля всегда идут в туннель, даже если в **Адресах маршрутов** перечислены только некоторые сети или частные сети идут в обход. Со списком маршрутов по умолчанию в туннель и так идёт всё.
- **Исключённые приложения**: приложения, которые **Контроль доступа** выводит из VPN, или все приложения вне списка в режиме «только выбранные», попадают на привязанные сайты мимо привязки. Страница предупреждает о них.
- **Kill switch**: только на Android. Страница показывает, включены ли для ReClash **Постоянная VPN** и **Блокировать подключения без VPN**, и открывает системные настройки VPN. Когда они включены, Android блокирует трафик, пока VPN выключена: привязанные сайты остаются недоступны после остановки ReClash, но и всё остальное тоже, а приложения, исключённые из VPN, могут остаться без сети.

Эти параметры применяются при запуске VPN. Если включить или выключить привязку или изменить её адреса, пока VPN работает, ReClash предложит перезапустить VPN, как и для других настроек VPN.

## Ограничения

- **macOS** получает только слой ядра: когда ядро остановлено, привязанные сайты ничто не блокирует, а kill switch там нет.
- **Linux и Windows**: [kill switch](kill-switch.md) на компьютере блокирует весь трафик вне TUN, а не только привязанные сайты.
- **Android** добавляет только меры VPN из раздела выше: когда ядро остановлено, привязанные сайты блокирует лишь системный kill switch.
- **TUN выключен**: привязка действует только на трафик, который идёт через ядро, а системный файрвол ничего не блокирует.
- **Сниффинг**: доменные записи сравниваются с именем соединения, а соединение, имя которого ядро не разрешало само, например у браузера со своим DNS, приходит голым адресом. Поэтому, пока включена привязка с доменными записями, ядро читает имя из TLS, HTTP и QUIC на их обычных портах, даже если в профиле сниффер выключен; профиль со своим сниффером сохраняет его. Имя влияет только на выбор правила, соединение уходит на тот же адрес, но доменные правила профиля теперь тоже могут ловить такие соединения.
- **Encrypted Client Hello**: браузер, скрывающий имя сайта через ECH, как Chrome и Firefox на многих сайтах за Cloudflare, показывает только публичное имя провайдера, поэтому такое соединение совпадает лишь с адресными записями, если имя не разрешало само ядро.
- **Записи только для ядра**: записи, которые системный файрвол повторить не может, — отрицание атрибутов geosite, регулярные выражения с lookaround, логические и портовые правила, а на Windows ещё ключевые слова и регулярные выражения — держатся только пока работает ядро. Страница перечисляет привязки с такими записями.
- **Изменения у провайдера**: привязка сверяет определения серверов в профиле, а не адрес, с которого трафик в итоге выходит. Если провайдер сменил выходной IP за тем же сервером или направил доменное имя сервера на другую машину, привязка этого не заметит.
- **Домены не из списка**: домен сервиса, не попавший ни в одну запись, идёт по правилам профиля. Пресеты охватывают запросы, замеченные при их составлении; проверьте, к каким доменам сервис обращается на самом деле, и добавьте недостающие.
- **Зашифрованный DNS в браузерах**: DNS over HTTPS и DNS over TLS идут мимо DNS-фильтра Helper. Пока ядро работает, это не важно, но после его падения такой браузер может разрешить и открыть привязанный сайт. Выключите безопасный DNS в браузере: в Chrome — **Настройки → Конфиденциальность и безопасность → Безопасность → Использовать безопасный DNS**, в Firefox — **Настройки → Приватность и защита → DNS через HTTPS**.
- **Зашитые адреса**: приложение, которое подключается по заранее известному адресу, ловится только адресными записями. Для таких сервисов добавьте записи `IP-CIDR`.
